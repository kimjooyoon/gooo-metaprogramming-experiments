# Laya serve.py concurrency review

Read-only inspection of the installed Laya 0.3.21 runtime on 2026-09-30. Source: `/tmp/meta-ontology-go-laya-venv-20260930/lib/python3.11/site-packages/laya/serve.py`  
SHA-256: `6e1bba24f89a47f41c05047d455d8dbcb8a88d958f08836e3b475407af8fa5ed`

## Findings

- **Model inference is serialized by this endpoint.** The service creates `ThreadPoolExecutor(max_workers=1)` (`serve.py:338–345`) and submits `router.predict(...)` through it (`480–492`). It also wraps the await in one `asyncio.Lock` (`478–491`), so non-cancelled endpoint handlers wait at the gate too. A single worker means inference jobs from this endpoint cannot execute simultaneously; this is a runtime property, not just a throughput-test assumption.
- **Admission is bounded separately from inference.** `LAYA_MAX_CONCURRENT` defaults to 16; unset/empty, invalid, or non-positive values resolve to 16 (`75–78`, `116–125`). The semaphore slot is acquired before reading the request body and held through handler completion (`350–356`, `425–442`). Once all slots are occupied, the route returns HTTP 503 with `Retry-After: 1` instead of admitting another request (`431–437`). Thus the setting is a cap on admitted requests, not concurrent model forwards.
- **An 8-second caller timeout does not imply inference stops.** `serve.py` has no per-request 8-second timeout or explicit disconnect/cancellation handler (the route only awaits the executor future). If the ASGI handler is cancelled while awaiting an already-running `router.predict`, cancellation cannot stop that synchronous function in its worker thread. The coroutine can unwind its lock/semaphore contexts while the thread continues, after which another request may submit work that queues behind it in the one-worker executor. If disconnect does not cancel the handler, it instead keeps the gate and admission slot until inference completes. Which path a particular client timeout takes depends on client and ASGI-server cancellation behavior, not established by this file. Either path can produce later-request delay; this inspection did not run a cancellation test.
- **This is not evidence of deadlock.** It establishes serialization and possible head-of-line delay/resource occupancy. The shown code does not establish a circular wait. Shutdown uses `pool.shutdown(wait=True, cancel_futures=True)` (`358–365`), so shutdown can wait for a running inference; that alone is not a deadlock unless the inference itself never returns or is blocked elsewhere.

These statements describe the installed implementation, not an assertion that the earlier experiment observed a timed-out request or that synthetic/local score trials exercised HTTP cancellation. No server was started or changed for this review.
